# 無感跨裝置存檔同步（重設計）

日期：2026-07-10
狀態：已定案
取代：`2026-06-22-cloud-save-design.md` 的雲端同步部分（zip 導出／導入保留，僅搬位置）

## 目標

登入後，遊戲存檔在不同裝置間全自動同步：

- **零按鈕**：健康狀態下工具列沒有任何雲端存檔 UI。
- **零對話框**：衝突逐槽自動合併，同槽衝突以較新者勝，從不詢問。
- **零 reload**：拉回雲端存檔不重新載入頁面。
- 不登入 → 一切如舊（純本機 IDBFS），不打擾。

後端沿用 Firebase（Firestore＋Google 登入，`web/account.js` 地基不動）。

## 非目標

- 免登入的裝置配對／同步碼。
- 即時對戰式的毫秒級同步；秒級即可。
- 改動引擎 C++（僅用 JS 端 hook；引擎 patch 是保底路線之外的最後手段）。

## 資料結構（Firestore）

```
users/<uid>/saves/<slug>                 { updatedAt, slots: { "Save01.lsd": { fp, updatedAt }, … } }
users/<uid>/saves/<slug>/files/<檔名>     { data: Bytes, updatedAt }
```

- **逐槽指紋** `fp = crc32(內容) + ":" + size`。crc32 直接重用 `_SAVE_UI`（`pwa.py`）打 zip 用的現成實作。取代舊設計「整組檔名+大小清單」的粗指紋。
- 同步對象＝存檔資料夾內所有檔案（沿用 `saveDir()` 尋徑），單檔 ≤ 900KB，超過略過。
- 安全規則不變：`users/<uid>` 僅本人可讀寫。
- 本機側記錄「上次同步狀態」：`localStorage['ep-savesync-<slug>'] = { "Save01.lsd": fp, … }`（逐槽，取代舊的整組 fp 字串）。

## 同步引擎（`web/savepanel.js` 重寫）

三個時機，取代舊的「開頁比對＋30 秒輪詢＋pagehide 補救」：

### 1. 開機閘門（開頁拉回，免 reload）

- 遊戲頁以 `Module.preRun` ＋ `addRunDependency('cloudsave')` 扣住引擎啟動。
- 期間讀一次雲端 manifest（**2 秒超時**；未登入、離線、超時、讀取失敗 → 立即放行，純本機開機）。
- 依逐槽合併規則（見下）把「雲端較新」的槽位寫進 FS，再 `removeRunDependency` 放行。
- 標題畫面「繼續遊戲」一出現就是最新存檔，全程無 reload。

### 2. 存檔即推（syncfs hook）

- 引擎存檔後會從 C++ 呼叫 `FS.syncfs()`（`players/official/index.js` 的 `ASM_CONSTS` 確認存在）。
- JS 端包一層 `easyrpgPlayer.FS.syncfs`：原函式完成後逐槽比指紋，有變化的槽批次上傳（一個 `writeBatch`：變更槽的 files docs ＋ manifest）。
- 去抖數秒，避免連續存檔重複上傳。取代 30 秒輪詢；`pagehide` 保留為最後防線。

### 3. 雲端即拉（onSnapshot）

- 對 manifest 文件掛一個 `onSnapshot` 監聽（每遊戲頁恰一個）。
- 別台裝置上傳後秒級收到；依合併規則把該拉的槽寫進 FS ＋ `FS.syncfs(false)`。
- 引擎每次打開讀檔選單都重掃存檔資料夾 → 玩家按「繼續／讀檔」時看到的即是最新，體感上等同「按下時重抓」。

## 逐槽三方合併（純函式）

每槽比較 本機 fp／雲端 fp／上次同步 fp：

| 本機 vs 上次 | 雲端 vs 上次 | 動作 |
|---|---|---|
| 沒變 | 沒變 | 無事 |
| 沒變 | 變了 | 拉（雲端寫進本機） |
| 變了 | 沒變 | 推（本機上傳） |
| 變了 | 變了 | 比 `updatedAt`，較新者勝（本機時間用 `FS.stat` mtime，雲端用 manifest updatedAt） |
| 槽只存在一邊，上次同步**沒有** | — | 新增：存在的一邊勝，傳播到另一邊 |
| 槽只存在一邊，上次同步**有** | — | 刪除：缺席的一邊代表刪除，傳播到另一邊（存在側若在刪除後又改過＝雙邊衝突，改走較新者勝） |

- 抽成純函式 `decideSlots(local, cloud, lastSynced) → { pull: […], push: […] }`，開機閘門、onSnapshot、即推共用同一支。
- 這是全設計唯一的分支複雜度所在，附一個最小可跑測試覆蓋上表各列。

## UI：按鈕＝狀態指示器

工具列（`_SAVE_UI`，`pwa.py`）的「存檔」鈕改為條件顯示：

- **已登入且同步健康 → 不顯示任何鈕。**
- **未登入 → 「☁ 同步」**：點擊即 Google 登入＋一句話說明；登入成功按鈕消失。
- **同步連續失敗（重試仍失敗）→ 「☁⚠」**：點開維修面板——錯誤原因＋手動「立即上傳／立即取回」（舊手動邏輯降級為僅故障時可見的救援通道）。
- **zip 導出／導入**搬進「下載」鈕：下載鈕改開小面板（下載遊戲 zip／導出存檔 zip／導入存檔 zip）。免登入備份與救災通道保留不變。

按鈕的存在即訊息：看得到＝有事要處理，看不到＝一切都好。

## 錯誤處理

- 任何同步失敗都不彈窗；靜默重試（下次時機再試），連續失敗才浮現「☁⚠」。
- 開機閘門一律 fail-open：雲端有問題絕不擋玩遊戲。
- 上傳與 manifest 更新同一個 `writeBatch`，不會出現「檔案傳了、manifest 沒更新」的半套狀態。

## 額度

每遊戲頁 1 個 onSnapshot 常駐監聽；每次存檔一批寫入（變更槽數＋1 docs）。遠低於 Firestore 免費額（讀 50k／寫 20k 每日）。

## 風險與保底

實作第一步先驗證兩個時序假設，任一不成立即退保底：

1. `preRun` 閘門與 IDBFS populate（`FS.syncfs(true)`）的先後順序——雲端槽寫入必須落在 populate 之後，否則會被本機蓋掉。
2. 引擎讀檔選單每次打開都重掃存檔資料夾（中途寫入的槽要能出現）。

保底路線：開機閘門退回「pull 完 `location.reload()` 一次」；即拉退回「僅開機時拉」。逐槽合併與即推不受影響。

## 測試

- `decideSlots()` 純函式：一個最小測試覆蓋合併表各列（新增、刪除、單邊變更、雙邊衝突）。
- 建置端（`pwa.py` 工具列改動）：沿用現有 `tests/test_pwa_*.py` 模式補斷言。
- 端到端：兩個瀏覽器 profile 登同帳號、同遊戲，A 存檔 → B 讀檔選單見新槽；A、B 各存不同槽 → 兩邊最終都有兩槽。
